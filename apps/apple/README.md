# Native Apple implementation

This directory contains the shared Swift 6 `FrankenTermKit` package and the native Xcode project for the first offline workspace-transfer slice. It is implementation source, not a signed or device-qualified terminal release.

## Entry points

Open `apps/apple/FrankenTerm.xcodeproj` with a stable Xcode supporting the iOS 26 SDK and Swift 6. The shared `FrankenTerm` scheme builds the iPhone/iPad application; `FrankenTermExport` builds the macOS companion (macOS 14 deployment floor). Both link the local package. There are no remote package downloads, generated project scripts, or build-time network dependencies. Development device signing needs the operator's selected team; no team or signing secret is embedded here.

The iOS app provides a native camera scanner, explicit transfer selection, bounded observation admission, authenticated package review, transaction-owned Keychain import, encrypted-file and ordinary public `.ftworkspace` import (including Open in FrankenTerm), and a machine/group browser preserving colors and ordering. Public documents need no transfer code and are clearly identified as unauthenticated, with no included private keys. Review and saved-workspace screens obtain credential availability, mandatory policies, host rejection, and dependent jump-route requirements from protected storage. It is single-scene until terminal/session ownership is integrated. It does **not** start SSH sessions, render a pretend shell, or execute imported auto-connect preferences.

The Mac companion opens a **preexisting local `.ftworkspace` JSON document**, lets the user select one or more machine groups, and previews the complete route, jump-host, trust, theme, and credential dependencies. Every canonical identity requires an explicit include-private-key or keep-reference-only decision. It accepts matching **unencrypted OpenSSH Ed25519 and ECDSA P-256/P-384/P-521 key files**, releases excluded key material, and reports concrete omissions and blocked routes before encryption. Selection changes invalidate the previous approval, code, and QR presentation.

It offers live fountain-coded QR playback with periodic source replay, targeted page repair, 3/5/10-symbol-per-second timing, separately revealed transfer codes, encrypted `.ftairgap` saving, saved **lossless APNG**, and a new **verified MP4** path. Each newly prepared transfer gets a fresh bundle identity; playback and saves reuse its exact frozen envelope. The phone lists unfinished page numbers matching the Mac's Repair menu and can restart one unfinished page while retaining verified pages and the selected source. The companion does not yet capture a running desktop FrankenTerm workspace automatically. Encrypted key files, RSA, certificates, executable configuration, and recipient-bound encryption remain unsupported.

## Implemented invariants

- `WorkspaceStore` serializes the journal, Keychain ownership, and catalog publication under an exclusive persistence lease. Before deleting staged or retired identities, recovery reaffirms the selected catalog's **durability**. Reading renamed bytes after a failed fsync alone does not authorize deletion.
- Import confirmation is tied to an exact decrypted candidate and previously reviewed saved revision. Existing local revocation denies resurrection from an old recording. Missing device keys can be restored from the same backup without duplicating surviving keys.
- The durable catalog remembers accepted bundle/transfer identities, rejects conflicting reuse before staging keys, and requires separate local approval to restore an earlier accepted export. Bundle identities are bound to their exporter across workspaces; transfer IDs and envelope digests cannot be rebound across namespaces. Canonical host-key revocations and mandatory trust requirements survive renamed trust records, replacement, and approved rollback. Migrated transfer identities use the same journal; recovery checks the accepted identity as well as workspace bytes.
- Catalog version four migrates the original single-candidate store, published version-two import history, and published version-three endpoint denials. Every accepted identity, digest, first revision, and global endpoint rejection is preserved. Additional effective-host alias denials and mandatory host-policy requirements survive replacement and approved rollback. The native browser obtains actual Keychain availability and durable local policy in one revision-consistent snapshot, and clears availability on deactivation or protected-storage failure.
- Host-key rejection persists by canonical host and port, independently of imported record IDs. DNS/IDNA, IPv6, and mapped IPv4 spellings cannot remove it. Negative fingerprints take precedence over algorithm labels and positive pins, including a presented certificate authority; certificates themselves still require a future qualified implementation. Every jump hop contributes its own readiness requirements.
- Credential reuse binds both the canonical public fingerprint and algorithm. An import without private material cannot relabel an existing Keychain identity. Matching aliases share material while retaining route-specific candidate order and authentication policy. A blocked candidate does not prohibit a separate permitted candidate.
- The manifest uses the comprehensive plan's ordered `credential_refs` and `authentication_methods`. Strict core allowlists exclude untyped settings; bounded optional namespaced extensions are discarded before persistence or re-export. Route readiness evaluates every jump, available identities, host pins/revocations and required capabilities independently. The current-plan example is an executable fixture, including mux route policy; this does not implement a mux transport.
- The published catalog contains public manifest bytes and account references, not private containers. `connectLater` remains persisted through restart. Keychain items are device-only, passcode-bound, user-presence protected, nonsynchronizable, and created without overwriting existing accounts.
- `OfflineRestore` distinguishes ciphertext reconstruction, authentication, review, commit, and recovery. Wrong-code retries preserve ciphertext. Suspension discards decrypted previews and retires observation generations. An uncertain publication is reconciled, not blindly repeated.
- A QR observation cannot silently change the selected source. Eight bounded strings feed one consumer; there is no task-per-camera-frame fanout. The scanner does not open QR URLs or retain camera images.
- Live playback periodically repeats rotating source fragments while fresh repair sequence numbers continue increasing, so late arrivals can recover even if mixed repair frames are missed. The phone can reset one unfinished page while retaining verified pages and fencing queued callbacks from before the reset.
- Private-key validation binds the manifest algorithm and fingerprint, outer public blob, inner public point and derived private identity. Archive construction and decoding validate bounded portability findings and inactive annotations against retained workspace entities.
- Portability records must reference retained entities; required unresolved conditions block their affected routes and dependent hops. Only registered boolean/opacity public desktop annotations may enter the catalog. Unknown optional opaque values are discarded with a content-free notice; unknown required values reject. Older catalogs are sanitized and durably migrated before publication, without changing accepted export identities or allowing failed migration to delete journal-owned keys. Network imports still require the current manifest format.
- The Mac removes the QR surface and invalidates pending raster results before revealing the code. The animation encoder accepts **only ciphertext**, not an application-window screenshot or a transfer code.
- Saved recordings contain every systematic symbol and a repair set. Each APNG frame, timing, loop metadata, and reconstructed envelope are verified before its final name is published. Existing destinations are not overwritten. Larger recordings are rejected before rendering rather than truncated; the initial saved path caps 256 frames, 1024-square raster input, and 128 MiB output. Live transfer remains available for larger bounded envelopes.
- The MP4 writer consumes a typed ciphertext-only source, encodes a bounded 1024-square H.264 stream at 30 fps, then decodes every output frame and verifies its QR payload, presentation time, hold duration, and reconstructed envelope. It caps 1,024 symbols, 9,000 video frames, 256 MiB, and a cooperative 600-second deadline, uses a bounded pixel-buffer pool, and excludes audio and custom metadata. Publication refuses existing destinations, uses an exclusive rename, and synchronizes the file and containing directory. A post-publication durability error retains the valid file and is reported distinctly. Native SDK/codec and physical-camera qualification remain outstanding; the current Core Image renderer uses a common integer module scale but does not force a fixed QR version.

## Verification status and commands

The complete shared package's **165 Linux XCTest cases passed**, with **zero failures or compiler warnings**, using Swift 6.2.1 after integration with the concurrent main changes. Coverage includes cryptographic and multipart-UR vectors, all 8,340 single-byte FTAG corruptions, both independently generated OpenSSH ECDSA fixture sets for all three curves, late-arrival source replay, public-document restoration, explicit group/key export decisions, exact numeric preservation, negative-fingerprint precedence, credential aliases and permitted alternatives, required-policy propagation, page repair, metadata boundaries, and portable MP4 timing/reconstruction. Publication fault tests cover original imports, migrated transfer-identity bindings, sanitization of legacy public metadata, and actual published version-three catalogs before and after migration writes. All previously published portable suites remain included.

```sh
swift test --package-path apps/apple/FrankenTermKit -j 2
```

This Linux command uses OpenSSL only as the package's independent test oracle. Apple products use CryptoKit and never link that test-only target. `AppleOpticalPresentationTests` and `AppleOpticalVideoTests` are intentionally Apple-only and are **not** included in the Linux result. The four video tests cover decoded pixels/timing/reconstruction, cancellation and reuse, refusal of an existing destination, and a destination created during encoding.

The Xcode project and Info.plist passed structural parsing; both application Swift files and the native video source/tests passed syntax parsing. **No Apple SDK type-check, native app build, Keychain/device test, camera capture, APNG/MP4 codec run, or performance qualification was available in this session.** Those are still required. A parser pass or Linux conditional build does not establish that the Apple-only branches compile. Run the native package tests and both app schemes on the repository's authorized Mac build environment, then exercise a passcode-enabled iPhone with the debugger detached for lifecycle tests.

Release distribution must use the repository's DSR system after its native iOS lane is implemented. Development Rust work remains subject to RCH; this Swift slice introduces no Cargo build step or fallback.

## Critical continuation

The next terminal slice is the actual iOS-buildable Rust terminal/renderer bridge, bounded SSH driver, native text input, exact source/control ownership, and real mux attachment. The Mac's typed live-workspace snapshot needs to feed the same export engine, replacing manual manifest selection. Encrypted OpenSSH import, RSA/certificate qualification, and HPKE recipient mode remain explicit capabilities to implement.

Native qualification must specifically verify Keychain metadata-only queries under the chosen ACL, protected-storage interruption, CryptoKit ECDSA behavior, source selection and page repair during camera loss, code concealment during app deactivation, current Image I/O APNG and AVFoundation/Vision MP4 behavior, symbol density and fixed-version QR requirements, and physical display/camera decoding at every offered speed. Device and SDK evidence must not be inferred from the portable tests.
